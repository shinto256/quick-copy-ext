# Phase 0: Research — グループナビゲーション改善

**Feature**: `006-group-navigation` | **Date**: 2026-09-04 | **Spec**: [spec.md](./spec.md)

spec の Assumptions で「計画・実装フェーズで具体化する」とした項目、および `/speckit.clarify` の
カバレッジ報告で Outstanding とした項目を解決する。設計の全体像は
`docs/superpowers/specs/2026-09-04-group-navigation-design.md` に記述済みで、本ドキュメントは
その決定の根拠と、計画フェーズで詰めた具体値を残す。

---

## R-001: ドラッグ&ドロップの実現方式

**Decision**: Pointer Events（`pointerdown` / `pointermove` / `pointerup` / `pointercancel`）と
`setPointerCapture` を使う。HTML5 drag and drop API（`dragstart` / `dragover` / `drop`）は使わない。

**Rationale**:

- HTML5 drag and drop API のドラッグ画像は要素の静止スナップショットで、FR-014（移動先の行を退避させて
  挿入位置を視覚的に示す）に必要な演出を制御できない。
- 同APIはタッチ操作に対応せず、Pointer Events はマウス・トラックパッド・タッチ・ペンを1つの
  イベントモデルで扱える。
- `setPointerCapture` により、ポインタが行の外へ出てもイベントを取り続けられる。狭いサイドパネルで
  長距離を移動する本機能では必須。
- `pointercancel` が FR-017（ドラッグ中断時に元の順序へ戻す）の受け口としてそのまま使える。

**Alternatives considered**:

- **HTML5 drag and drop API**: 上記の理由で却下。
- **ドラッグ&ドロップライブラリ（SortableJS等）の導入**: technical.yaml の「ビルドツールを導入せず
  ノービルドで配布する」「Vanilla JS採用」の既定方針に反する。本機能に必要な範囲は約180行で収まる
  （プロトタイプで実測）ため、依存追加の見返りが小さい。
- **`▲▼` ボタンと「先頭へ移動」による並び替え**: 既存の項目並び替え（`sidepanel.js` の `moveItem`）と
  同じパターンで実装リスクは低いが、ドラッグの操作性を優先して却下（design.md の「検討した代替案」参照）。

## R-002: 挿入位置の算出方法と行の高さの扱い

**Decision**: 各行の位置と高さを**ドラッグ開始時に1回だけ計測**し、ドラッグ中は再計測しない。
挿入位置は「掴んだ行の中心が、他の何行の中心を越えたか」で求める。行の高さが揃っていなくても
成り立つため、可変高のリストにも使える。

**Rationale**:

- `pointermove` ごとに `getBoundingClientRect` を呼ぶと移動中の負荷が上がる。ドラッグ開始時の
  1回の計測で必要な情報（各行の相対位置・高さ・行間の余白）が揃うため、移動中の計測が不要になる。
- 行の位置はコンテナ内の相対オフセットとして持つ。スクロールしても値が変わらないので、
  自動スクロール中も再計測せずに済む。
- 退避量は「掴んだ行の高さ + 行間の余白」で、行が抜けたときに下の行が繰り上がる量と一致する。
  高さが揃っていない場合もこの値は共通なので、可変高でも正しく動く。
- 計測をCSS側の実測に任せることで、行高をJS定数として二重に持たずに済み、フォント設定や
  ズームの変化にも追従する。

**Alternatives considered**:

- **行高を一定と仮定し `Math.round(移動量 / 行高)` で求める**: 実装は最も単純だが、可変高のリストに
  使えない。当初はこの案を採ったが、後に項目一覧（高さが値の長さで変わるカード）へ適用する必要が
  生じたため、上記の中心比較方式へ一般化した。グループの縦リストは行高が一定なので、
  一般化しても挙動は変わらない。
- **行高をJS定数とCSSに二重定義**: 値の乖離が事故になるため却下。

**Constraint for implementation**: グループの縦リストは1行に収めて末尾省略する（FR-024）。
可変高に対応済みだが、行高が揃っている方が挿入位置の見当がつけやすい。

## R-003: ドラッグ開始と判定する移動距離（FR-009a）

**Decision**: **5px**。`pointerdown` の座標から5px以上動いた時点でドラッグ開始と判定する。
5px未満のまま `pointerup` した場合はグループ切替（FR-005）として扱う。

**Rationale**:

- 5px は主要ブラウザのネイティブなドラッグ判定およびリスト並び替えUIで広く使われる値で、
  クリック時の微小なポインタぶれ（通常1〜2px）を吸収できる。
- 行高は44px想定なので、隣の行と入れ替わるには約22pxの移動が必要になる。5pxで持ち上げ演出が
  始まることで、入れ替わる前に「掴んだ」フィードバックが返る。
- 大きすぎる閾値（10px以上）は並び替えの開始が重く感じられ、小さすぎる閾値（2px以下）は切替のつもりが
  並び替えになる誤操作を招く。

**Alternatives considered**:

- **3px**: 誤操作のリスクが上がる。
- **10px**: 並び替えの開始が重い。
- **長押しでドラッグ開始**: `/speckit.clarify` Q4 で選択肢Cとして提示し、閾値方式（A）が選ばれた。

## R-004: ドラッグ中の演出パラメータ

**Decision**: プロトタイプで確認した以下の値を採用する。

| パラメータ | 値 |
|-----------|-----|
| 兄弟行の退避アニメーション | `transform: translateY(±行高)`、`transition: transform 160ms cubic-bezier(0.2, 0.8, 0.2, 1)` |
| ドロップ時の吸着 | 最終位置へ `transform` を `180ms` の同イージングで遷移させ、完了後にDOMを確定して `transform` を解除 |
| ドラッグ中の行 | `z-index` を上げ、影を付けて浮かせる |
| 自動スクロールの発動範囲 | 縦リストの上端・下端から `30px` 以内 |
| 自動スクロールの速度 | 1フレームあたり `11px`（`requestAnimationFrame` ループ） |

**Rationale**:

- 上記の値は `.superpowers/brainstorm/1623-1788490403/content/dnd-prototype-v2.html` の動作確認で
  「入れ替わっている感」が得られることを確認済み。
- DOMの確定をアニメーション完了後に行うことで、確定時のレイアウト変化によるカクつきを避けられる。
- 自動スクロールを `requestAnimationFrame` で回すことで、`pointermove` が発生しない静止状態でも
  スクロールが継続する（端で止めたまま送りたいケースに対応）。

**Alternatives considered**:

- **Web Animations API (`element.animate()`)**: CSS Transitions で足りる範囲であり、完了検知も
  `transitionend` または固定時間の `setTimeout` で済むため導入しない。
- **アニメーションなしで即座にDOM入れ替え**: FR-014 を満たせない。

**Note**: SC には演出の応答性の数値目標を置いていない（`/speckit.clarify` の Outstanding 項目）。
上記の遷移時間を本ドキュメントの決定として固定し、受け入れは `quickstart.md` の目視確認で行う。

## R-005: 並び順の情報源とストレージキーの設計

**Decision**: 新規キー `tabOrder`（`string[]`）を追加し、タブの並び順の唯一の情報源とする。
既存の `groups` 配列は集合として扱い、配列順を順序情報に使わない。未分類は
`"__unassigned__"` センチネルで表す。

**Rationale**:

- 未分類は `groups` に実体を持たない仮想タブなので、`groups` の配列順だけでは「未分類を並び替える」
  （FR-010）を表現できない。
- 順序を1つの配列に集約すると、並び替えの永続化が「配列を丸ごと保存する」1操作になり、
  `groups` と順序の二重管理を避けられる。
- 既存の `groups` データはスキーマ変更なしでそのまま読める（マイグレーション不要）。`tabOrder` が
  未保存の状態では正規化によって「未分類が先頭、以降は `groups` の配列順」となり、現在の表示順と一致する。

**Alternatives considered**:

- **`groups` 配列に `order` フィールドを追加**: 未分類を表現できず、既存データへのフィールド追加
  （マイグレーション）が必要になる。
- **`groups` 配列に未分類のプレースホルダを実体として入れる**: `groupRepository.list()` が実グループ
  だけを返すという既存契約が崩れ、`itemRepository` 側の `groupId` の扱いにも影響が出る。
- **`settings` に未分類の位置（index）だけを保存**: グループの並び替えと未分類の位置の相対関係を
  保つロジックが複雑になり、2つの情報源の整合を自分で維持する必要が出る。

## R-006: `tabOrder` の書き込み契機

**Decision**:

- **`reorderTabs(orderedTabIds)` が主たる書き込み口**。並び替え確定時に正規化済みの配列を丸ごと保存する。
- **`remove(id)` は `tabOrder` から該当IDを除去する**。グループ削除は明示的な契機であり、除去しておかないと
  作成・削除を繰り返すたびに実在しないIDが蓄積する。
- **`create(name)` は `tabOrder` を書き込まない**。正規化が「`tabOrder` に含まれないグループを末尾に
  追加する」ため、FR-019 の「新規グループは末尾」は書き込みなしで保証される。

**Rationale**:

- 書き込み口を絞ることで、順序が意図せず変わる経路を減らせる。
- 読み出し時の正規化（R-007）があるため、`create` 側の書き込みは冗長になる。
- 一方で削除は放置すると蓄積するため、発生元で刈り取るのが最も単純。

**Alternatives considered**:

- **`listTabOrder()` が正規化で変化があったら書き戻す（read-repair）**: 刈り取りと末尾追加を1つの
  コードパスにできるが、読み出し関数が書き込みを行うため呼び出し側から挙動が読みにくい。
- **`create` / `remove` のどちらも書き込まない**: 実在しないIDが無制限に蓄積する（実害は小さいが
  保存データが汚れる）。

## R-007: `tabOrder` の正規化ルール

**Decision**: `normalizeTabOrder(storedOrder, groups)` を純関数として `src/storage/tabOrder.js` に置き、
読み出しのたびに適用する。ルールは以下の順に適用する。

1. `groups` に存在しないIDを除去する（削除済みグループ、壊れた保存データ）
2. 重複IDは最初の出現のみ残す
3. `"__unassigned__"` が含まれていなければ先頭に追加する
4. `tabOrder` に含まれていない `groups` のIDを、`groups` の配列順で末尾に追加する

**Rationale**:

- 正規化を読み出し側に置くことで、保存データがどんな状態でもFR-019（重複表示・欠落が0件）を満たせる。
  拡張機能の更新やストレージの手動編集で不整合が生じても表示が壊れない。
- 純関数なのでDOMも `chrome` APIも不要で、ユニットテストで全ルールを網羅できる。
- 正規化後の要素数は最大51（グループ上限50 + 未分類1）で、毎回の実行コストは無視できる。

**Alternatives considered**:

- **保存時にのみ検証して読み出しは信頼する**: 保存経路以外（拡張の更新、他バージョンからの移行）で
  壊れたデータに対処できない。
- **不整合を検出したらエラーを投げる**: 利用者が復旧できないため、自己収束の方が適切。

## R-008: `UNASSIGNED_TAB_ID` の定義位置

**Decision**: `src/storage/tabOrder.js` で定義し、既存の `src/sidepanel/itemFilter.js` からは
再エクスポートする。

**Rationale**:

- センチネルは `groupRepository`（storage層）と `groupPanel`・`sidepanel`（UI層）の双方が必要とする。
  現在の定義位置（`sidepanel/itemFilter.js`）のままでは storage層がUI層をimportする逆方向の依存になる。
- 再エクスポートにすることで、既存の import 経路（`sidepanel.js:6`、
  `tests/unit/itemFilter.test.js:2`）を変更せずに済み、既存テストもそのまま通る。

**Alternatives considered**:

- **両方に定数を定義**: 値の乖離が事故になる。
- **`itemFilter.js` の定義を残し `groupRepository` からimport**: 層の依存方向が逆になる。
- **既存の import 経路をすべて `storage/tabOrder.js` へ書き換え**: 差分が増えるだけで得るものがない。
  再エクスポートで十分。

## R-009: 所属項目件数の集計方法（FR-003）

**Decision**: パネルを開くとき（および内容更新時）に `itemRepository.list()` を1回呼び、
`groupId` ごとに件数を数えて `Map` に持つ。未分類の件数は `groupId === null` の項目数とする。
`itemRepository` に集計用の関数は追加しない。

**Rationale**:

- 項目上限は500件で、1回の走査で全グループ分の件数が求まる。グループごとに問い合わせる必要がない。
- 既存の `itemRepository.list()` をそのまま使えるため、storage層の契約を増やさずに済む。
- 削除確認に出す件数（FR-027）も同じ `Map` から取れる。

**Alternatives considered**:

- **`itemRepository.countByGroup()` を新設**: 内部で同じ走査をするだけで、storage層の関数が増える。
- **グループごとに `list()` をフィルタして数える**: グループ数×項目数の走査になる。

## R-010: 全グループパネルの表示方式

**Decision**: 既存の項目登録フォームと同じオーバーレイのパターンを踏襲する。
`position: fixed; inset: 0` のオーバーレイ（既存 `.form-overlay`、`sidepanel.css:627`）の中に
パネル本体を置き、`hidden` 属性で開閉する。

**Rationale**:

- `/speckit.clarify` Q1 で全面オーバーレイが選ばれた。既存に同じ構造（`#item-form-overlay` +
  `.item-form`）があるため、スタイルの考え方と開閉の実装を揃えられる。
- 縦リストの高さを最大限使えるため、グループ50個の一覧（FR-006）に有利。

**Alternatives considered**:

- **タブバー直下にインライン展開**: 50行でレイアウトが大きく動き、項目一覧が画面外へ出る。
- **ポップオーバー（既存 `.more-menu` / `.selection-group-change-popover` のパターン）**: 高さに
  上限を設ける必要があり、一覧できる行数が減る。

**Note**: 既存 `.item-form` は `max-width: 360px` で中央寄せだが、パネルは縦リストの表示領域を
最大化するため幅・高さをオーバーレイいっぱいに広げる。既存フォームのスタイルは変更しない。

## R-011: パネルを閉じたときの絞り込み文字列の扱い

**Decision**: パネルを閉じるとき（閉じるボタン、`Escape`、グループ切替のいずれでも）絞り込み文字列を
クリアする。次にパネルを開いたときは絞り込みなしの状態から始まる。

**Rationale**:

- 既存の `selectTab`（`sidepanel.js:713`）はタブ切替時に項目名検索をクリアする。同じ考え方に揃える。
- FR-008a でパネルを開くと絞り込み入力にフォーカスが当たるため、前回の文字列が残っていると
  「そのまま入力すると前回の続きに追記される」という分かりにくい挙動になる。
- FR-008b（開いたとき選択中のタブまでスクロール）は、絞り込みが残っていると選択中の行が
  絞り込みで消えている可能性があり、両立しない。

**Alternatives considered**:

- **絞り込み文字列を保持する**: 同じ絞り込みで連続して操作するケースに有利だが、上記のフォーカスと
  スクロールの挙動と噛み合わない。
- **グループ切替時のみクリアし、閉じるボタン・`Escape` では保持する**: 挙動が経路によって変わり
  説明しにくい。

## R-012: 既に保存されている20文字超のグループ名の扱い（FR-023）

**Decision**: `groupRepository` の検証は `create` / `rename` の入力に対してのみ行い、
既に保存されている名前は検証も切り詰めもしない。表示側は末尾省略（FR-024）で対応する。

**Rationale**:

- 上限を下げたことで既存データを黙って書き換えると、利用者が意図して付けた名前が失われる。
- 検証を入力時のみに限定するのは既存実装（`validateName` を `create` / `rename` の先頭で呼ぶ）の
  形をそのまま維持することであり、追加のマイグレーションコードが不要。
- パネルの縦リストは上限20文字が収まる幅（SC-008）なので、20文字超の既存名だけが省略される。

**Alternatives considered**:

- **読み出し時に20文字へ切り詰める**: データの黙った書き換えになる。
- **起動時にマイグレーションして切り詰める**: 同上。かつ元の名前が復元できない。
- **20文字超の名前がある間は警告を出す**: 利用者に対処を強いるだけで、末尾省略で読めるので不要。

## R-013: `dragReorder` の境界（将来のキーボード対応と項目一覧への流用）

**Decision**: `attachDragReorder(container, options)` は「並び替え後の要素の並びをコールバックで返す」
ところまでを担い、永続化とグループの概念を持たない。タップ（閾値未満）は `onActivate` で別途通知する。

**Rationale**:

- 永続化を含めないことで、キーボード操作による並び替えを後から足す際に、同じ `onReorder` の受け口へ
  つなぐだけで済む（spec Assumptions の「後から足せる境界で分離する」を満たす）。
- グループの概念を持たないため、項目一覧への流用（spec ではスコープ外）が可能な形になる。
- タップと並び替えの判定は同じポインタ操作の中で行う必要があるため（FR-009a）、`dragReorder` が
  両方を通知するのが自然。呼び出し側で `pointerdown` を二重に監視する必要がなくなる。

**Alternatives considered**:

- **`dragReorder` が直接 `groupRepository.reorderTabs` を呼ぶ**: storage層への依存が入り、
  項目一覧への流用ができなくなる。
- **タップ判定を呼び出し側の `click` イベントで行う**: ドラッグ後の `pointerup` でも `click` が
  発火するため、並び替えとグループ切替が同時に起きる（spec Edge Cases で「両方が同時に起きることは
  ない」としている挙動に反する）。

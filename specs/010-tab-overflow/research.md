# Phase 0: Research — タブバーの横スクロール廃止と幅追従表示

**Feature**: `010-tab-overflow` | **Date**: 2026-09-04 | **Spec**: [spec.md](./spec.md)

spec の Assumptions で計画フェーズ送りとした項目を決定する。

---

## R-001: タブの幅を測る方法

**Decision**: `renderTabs()` で全タブをDOMに描画した**直後に一度だけ**、各タブの
`getBoundingClientRect().width` を測って配列にする。その配列を使って表示可否を決め、
収まらないタブに `hidden` を付ける。

**Rationale**:

- グループ名の長さでタブの幅が変わるため、固定の個数では決められない（spec Assumptions）。
  実測が必要。
- 「全部描画してから隠す」順序にすれば、計測は1回で済む。1つずつ追加しながら幅を確認する方式は
  タブの数だけレイアウトの再計算が起きる。
- `hidden` を付ける前に測るので、隠す予定のタブも正しい幅が取れる。表示可否が変わったときに
  幅を測り直す必要がない。

**Alternatives considered**:

- **1タブずつ追加して溢れたら止める**: 追加のたびにレイアウトが再計算され、タブの数に比例して
  コストが増える。またすでに `hidden` にしたタブの幅が測れないため、幅を広げたときの再計算で
  もう一度描画が必要になる。
- **名前の文字数から幅を推定する**: 全角と半角、書体の字幅で誤差が出る。タブ名は
  末尾省略される（`006-group-navigation` FR-024）ため上限幅もあり、推定と実測がずれる。

**Note**: 幅の配列は再描画のたびに測り直す。グループ名の変更でタブの幅が変わるため
（spec US2 シナリオ7）、キャッシュしない。

---

## R-002: 幅の変化を検知する仕組み

**Decision**: `ResizeObserver` でタブバーの要素（`#tabs`）を監視する。通知を受けたら
**表示可否の再計算だけ**を行い、タブのDOMは作り直さない。

**Rationale**:

- サイドパネルは利用者が端をドラッグして幅を変えられる。`window` の `resize` イベントは
  サイドパネル自身の幅の変化では発火しないことがあるため、要素を直接観測する方が確実。
- `ResizeObserver` はレイアウト後に通知されるため、計測した幅が確定した値になる。
- 通知ごとにDOMを作り直すと、ドラッグ中に何度も再描画が走る。既に描画済みの要素の `hidden` を
  切り替えるだけなら、幅の配列（R-001 で測った値）を使い回せる。

**幅の配列の保持**: 直近の `renderTabs()` で測った幅の配列と、タブIDの配列を
モジュールスコープに持つ。`ResizeObserver` の通知ではこれを使って表示可否だけを再計算する。
`renderTabs()` が走れば新しい値に更新される。

**Alternatives considered**:

- **`window` の `resize` を使う**: サイドパネルの幅の変化で確実に発火する保証がない。
- **`ResizeObserver` の通知でも `renderTabs()` を呼ぶ**: ストレージの読み出しとDOMの再構築が
  ドラッグ中に繰り返される。表示可否は幅だけで決まるので、データを読み直す必要がない。

**Note**: サイドパネルが表示されていない状態（幅が0）では計算しない（spec Edge Cases）。
`ResizeObserver` は幅0の通知も送るため、幅が0のときは何もせずに返る。

## R-003: 表示するタブを決めるルール

**Decision**: 純関数 `visibleTabIndexes(tabWidths, availableWidth, gap, selectedIndex)` を
`src/sidepanel/tabOverflow.js` に置く。表示するタブのインデックスの集合（`Set`）を返す。

ルールは以下の順に適用する。

1. 並び順の先頭から、`幅 + gap` を積み上げて `availableWidth` に収まる範囲を表示候補にする。
2. 手順1の候補に `selectedIndex` が含まれていれば、それを結果とする（**他を余分に隠さない**。
   spec FR-008）。
3. 含まれていなければ、`selectedIndex` を必ず含めたうえで、先頭から詰め直す。
   選択中のタブの幅を先に確保し、残りの幅に先頭から入るところまでを追加する。
4. 選択中のタブすら収まらない場合も、`selectedIndex` だけは結果に含める（spec Edge Cases）。

`availableWidth` は「タブバーの内容領域の幅 − 末尾のボタンの幅 − そのボタンの前の `gap`」を
呼び出し側が計算して渡す。末尾のボタンは常に表示するため（spec FR-006）、先に幅を差し引く。

**Rationale**:

- 手順2があることで、選択中のタブがそのまま収まる通常のケースで余分な処理も余分な非表示も起きない。
- 手順3は「選択中のタブのための場所を作る」処理。先頭から詰め直すので、並び順の意味
  （先頭が優先）が保たれる。
- 手順4は狭すぎる場合の逃げ道。選択中のタブが見えないことは避ける（spec FR-005 / SC-004）方が、
  はみ出さないことより優先度が高い。ただしタブ名は末尾省略されるため、実際にはみ出す幅は
  タブ1個分に収まる。

**戻り値を `Set` にする理由**: 呼び出し側は「このタブを表示するか」を各タブについて問い合わせる。
配列だと毎回の検索が線形になる。

**Alternatives considered**:

- **表示する個数（先頭からN個）を返す**: 手順3で選択中のタブを含める場合、連続した範囲では
  表せない（先頭からN個 + 選択中の1個という不連続な集合になる）。
- **選択中のタブを常に先頭へ寄せて表示する**: 並び順が画面上で崩れ、利用者が決めた順序と
  タブバーの表示順が食い違う。

## R-004: 末尾のボタンの扱い

**Decision**: `.tab-panel-open` の `position: sticky; right: 0` を撤去する。`margin-left: auto` は
残す。

**Rationale**:

- `sticky` は横スクロールがある前提でボタンを右端に留めるための指定だった。横スクロールを
  廃止する（spec FR-001）ので不要になる。
- `margin-left: auto` は「タブが少ないときにボタンを右端へ寄せる」ために引き続き必要。
  タブの合計幅が足りているときに余った幅を吸収する。
- ボタンは `hidden` にする対象に含めない。常に表示する（spec FR-006）。

---

## R-005: 隠すタブの表現

**Decision**: `hidden` 属性を付ける。CSS の `display: none` が既定で適用される。

**Rationale**:

- `hidden` は要素をレイアウトから外すため、タブバーの幅に影響しない（`visibility: hidden` は
  領域を占めたままなので不適）。
- レイアウトから外れる要素はキーボードのフォーカス移動の対象にもならない（spec FR-013 / SC-006）。
  追加の指定が不要。
- 既存コードで開閉に `hidden` 属性を使っている箇所（オーバーレイ、`#group-panel-add` など）と
  表現が揃う。

**Alternatives considered**:

- **要素を作らない（描画しない）**: 幅を測れなくなる。R-001 の「全部描画してから隠す」と
  両立しない。
- **`visibility: hidden`**: 領域を占めたままなので、隠しても幅が足りない。

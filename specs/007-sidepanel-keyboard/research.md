# Phase 0: Research — サイドパネルのキーボード操作対応

**Feature**: `007-sidepanel-keyboard` | **Date**: 2026-09-04 | **Spec**: [spec.md](./spec.md)

spec の Assumptions で「計画・実装フェーズで具体化する」とした項目、および `/speckit.clarify` で
Deferred とした4件を決定する。

---

## R-001: 行をフォーカス可能にする手段

**Decision**: 縦リストの各行（`<li class="group-row">`）に `tabindex="0"` を付与する。
`role` は付けない（`listbox` / `option` にはしない）。

**Rationale**:

- spec FR-005 は「縦リストに表示されているすべての行をフォーカスの移動対象に含める。飛ばされる行が
  あってはならない」と定めており、US1 のシナリオ1・4・5は「絞り込み入力 → 行 → その行の三点リーダー」
  という素直なタブ順を前提にしている。各行を1つのタブストップにする `tabindex="0"` がこれに直接対応する。
- 行の内容を `<button>` で包む案は使えない。行には三点リーダーの `<button>` が入るため、
  ボタンの入れ子になり不正なHTMLになる。
- `role="listbox"` / `role="option"` を付けると、支援技術は「矢印キーで選択肢を移動し、Tabで抜ける」
  という操作を期待する。この期待に応えるには矢印単独をリスト内移動に割り当てる必要があり、
  R-002 で矢印を並び替えに使う決定と噛み合わない。ロールを付けずに素のタブストップとして扱う方が、
  実際の操作と支援技術への説明が一致する。
- フォーカス表示は既存のグローバルな `:focus-visible`（`sidepanel.css:114`。Yellow-300の内側 +
  黒の外周を `box-shadow` の二層で描く）が要素を問わず適用されるため、フォーカス可能にするだけで
  spec SC-007（既存のボタン・入力欄と同一の見た目）が成立する。CSSの追加は不要。

**Alternatives considered**:

- **行の内容を `<button>` で包む**: 三点リーダーのボタンと入れ子になるため不可。
- **`role="listbox"` + roving tabindex（リスト全体で1タブストップ、矢印で行間移動）**: グループが
  50個あるときタブストップが100個（行50 + 三点リーダー50）にならず、タブ移動の負担が小さい。
  ただし矢印単独をリスト内移動に取られるため並び替えのキーが別途必要になり、支援技術向けの
  ロール整合も追加で必要になる。**タブストップ数の懸念は残るが**、パネルを開くと絞り込み入力に
  フォーカスが当たる設計（`006-group-navigation` FR-008a）のため、想定される主要な流れは
  「絞り込んで候補を数件に減らしてから行へタブ移動する」であり、50行を順にタブ送りする経路は
  例外的と判断した。将来この負担が問題になった場合は、本決定を roving tabindex へ切り替えられる
  （行を `tabindex="-1"` にして矢印で移動させる変更で、並び替えのキーは維持できる）。

**Note**: `dragReorder` は行の `pointerdown` で `preventDefault()` を行っているため、
**行をポインタで押してもフォーカスは移らない**。ポインタで押した場合はグループが切り替わるため
実害はなく、spec の Assumptions に記載済み。この挙動は変更しない（FR-006 / SC-008 の回帰防止のため）。

## R-002: キーの割り当て

**Decision**:

| 操作 | キー |
|------|------|
| フォーカスした行のグループへ切り替える | `Enter` / `Space` |
| フォーカスした行を1つ上へ移動する | `Alt` + `↑` |
| フォーカスした行を1つ下へ移動する | `Alt` + `↓` |
| オーバーレイを閉じる / インライン編集を取消す | `Escape` |

**Rationale**:

- **`Enter` / `Space`**: ネイティブのボタンが両方で発火するため、`tabindex="0"` の要素をボタン相当に
  見せるうえで両方受けるのが素直。`Space` はページスクロールの既定動作を持つので、行にフォーカスが
  ある場合のみ `preventDefault()` する。
- **`Alt` + 矢印**: 「行を移動させる」操作の一般的な慣習で、多くのエディタやリストUIが採用している。
  ブラウザが使う `Alt` + `←` / `→`（履歴の戻る・進む）とは別のキーなので衝突しない。
  矢印単独を空けておけるため、R-001 の Alternatives に挙げた roving tabindex へ将来切り替える余地も残る。
- **`Escape`**: 全グループパネルでは既に実装済み（`groupPanel.js`）。項目登録フォームに同じ挙動を
  足して統一する（spec FR-020）。

**Alternatives considered**:

- **`↑` / `↓` 単独で並び替え**: 最も打ちやすいが、行にフォーカスしただけで矢印が並び替えになるのは
  予測しづらく、ページスクロールも奪う。
- **`Ctrl` + 矢印**: 一部アプリで使われるが、ブラウザやOSのショートカット（単語単位のカーソル移動、
  仮想デスクトップ切替など）と衝突しやすい。
- **`Shift` + 矢印**: 選択範囲の拡張という一般的な慣習と衝突する。

**Note**: `/speckit.clarify` でこのキー割り当てを質問したが、確認は不要との回答を得たため、
推奨していた `Alt` + 矢印を本ドキュメントの決定として採用する。

## R-003: 並び替え後のフォーカス復帰

**Decision**: 並び替えを確定したら `groupPanel` の再描画（`renderList()`）を行い、
**再描画後に `data-tab-id` が一致する行を探して `focus()` する**。

**Rationale**:

- `renderList()` は `listEl.innerHTML = ""` で作り直すため、移動前の行のDOM要素は失われる。
  同じ要素へフォーカスを戻すことはできない。
- `data-tab-id` は未分類のセンチネルまたはグループIDで、再描画をまたいで同じ行を一意に指す。
  これを鍵にすれば、移動した行へ確実にフォーカスを戻せる（spec FR-009）。
- 永続化に失敗した場合は保存済みの順序から再描画するが、同じ `data-tab-id` の行は存在し続けるため、
  同じ手順で「操作していた行」へフォーカスを戻せる（spec の Edge Cases）。

**Alternatives considered**:

- **DOM要素を作り直さず、既存の行要素を並べ替える**: フォーカスを保ったまま移動でき理想的だが、
  `renderList()` の作り直し方式を変えることになり、`006-group-navigation` の描画ロジック全体に
  影響する。本featureの範囲を超える。
- **フォーカスを絞り込み入力へ戻す**: 連続して移動できなくなり spec FR-009 を満たせない。

## R-004: 並び順配列の組み替えの置き場所

**Decision**: `src/sidepanel/listReorder.js` に純関数 `moveInList(list, index, offset)` として切り出す。
DOMにも `chrome` API にも依存させない。

**Rationale**:

- 境界での無変更（spec FR-011: 先頭で上へ、末尾で下へ移動しても順序を変えずエラーも出さない）は
  自動テストで担保したい条件だが、`groupPanel.js` に埋めるとDOM環境が必要になりテストできない。
- `006-group-navigation` で `tabOrder` の正規化を `storage/tabOrder.js` の純関数に切り出して
  ユニットテストで全ルールを網羅したのと同じ方針。
- storage層ではなくUI層に置く。並び順の組み替えは「利用者の操作を順序配列に翻訳する」UI側の関心であり、
  永続化と検証は既存の `groupRepository.reorderTabs()` が担う。

**Alternatives considered**:

- **`storage/tabOrder.js` に追加**: storage層は永続化と正規化の責務に留めたい。UI操作の翻訳を
  混ぜると層の役割が曖昧になる。
- **`groupPanel.js` にインラインで書く**: 境界条件をユニットテストできない。

## R-005: フォーカストラップの実現方式

**Decision**: `src/sidepanel/focusTrap.js` に `createFocusTrap(overlayEl)` を用意し、
`activate(returnFocusTo)` / `deactivate()` を返す。`document` の `keydown` を捕らえ、
`Tab` / `Shift` + `Tab` がオーバーレイ内の最後／最初のフォーカス可能要素を越えようとしたときに
反対側の端へ移す。

**Rationale**:

- フォーカス可能な要素の集合は開閉のたびに変わる（縦リストの行数、三点リーダーの有無、
  インライン編集中かどうか）。`keydown` の時点で毎回集合を求める方式なら、要素の増減を追う必要がない。
- `inert` 属性で背後をまとめて無効化する方式は、対象が「オーバーレイ以外のすべて」になり、
  サイドパネルの既存構造（ヘッダー・タブバー・一覧が兄弟要素）に対して指定漏れが起きやすい。
- 全グループパネルと項目登録フォームで同じ振る舞いが必要なため、オーバーレイ要素を渡すだけで
  使える形にして重複を避ける。

**フォーカス可能要素の判定**: `overlayEl.querySelectorAll()` で
`a[href], button:not([disabled]), input:not([disabled]), select:not([disabled]), textarea:not([disabled]), [tabindex]:not([tabindex="-1"])`
を取り、`hidden` 属性を持つ要素とその祖先が非表示のものを除く。

**Alternatives considered**:

- **`inert` 属性で背後を無効化**: 上記の理由で却下。
- **オーバーレイの前後に見えないフォーカス受け（sentinel）を置く**: DOM構造に見えない要素を足す必要があり、
  `focus` イベントの往復で実装が読みにくくなる。
- **フォーカストラップのライブラリを導入**: ノービルド方針に反する。必要な範囲は約60行で収まる。

## R-006: フォーカス復帰先の記憶

**Decision**: `activate(returnFocusTo)` の引数で復帰先を明示的に受け取る。
呼び出し側（オーバーレイを開く処理）が `document.activeElement` を渡す。
`deactivate()` の時点で復帰先が `document` から失われている場合は、フォールバックとして
オーバーレイを開く起点の要素（タブバー末尾のパネルを開くボタン、項目追加ボタン）へ戻す。

**Rationale**:

- `activate` の内部で `document.activeElement` を読む方式でも動くが、呼び出し側が
  「何に戻すか」を明示できる方が、フォールバックの指定（spec FR-019）を同じ場所に書ける。
- グループ削除で行が消えるケース（spec の Edge Cases）では、記憶していた行の要素が
  `document` から外れる。`document.contains(el)` で判定してフォールバックへ切り替える。

**Alternatives considered**:

- **常に起点の要素へ戻す**: 実装は単純だが、行にフォーカスした状態でパネル内の操作をして閉じたとき、
  毎回タブバーへ飛ばされる。spec FR-018（開いた時点でフォーカスしていた要素へ戻す）を満たさない。

## R-007: `Escape` の優先順位

**Decision**: `Escape` の処理は以下の順で判定する。

1. インライン編集の入力欄にフォーカスがある → 編集を取消し、オーバーレイは閉じない（spec FR-021）
2. 行メニュー（三点リーダーのメニュー）が開いている → メニューを閉じる
3. それ以外 → オーバーレイを閉じる

**Rationale**:

- 1 と 3 は `006-group-navigation` で既に実装済みの優先順位（インライン編集の入力欄が
  `keydown` を `stopPropagation()` するため、`document` のハンドラに届かない）。本featureでは
  この仕組みを維持する。
- 2 も既存実装のとおり。

**Note**: 項目登録フォームの `Escape` は新規追加。フォーム内の入力欄（名前・値・グループ選択）には
`Escape` の独自処理がないため、`document` のハンドラで受けてフォームを閉じる。閉じる処理は既存の
`closeItemForm()` をそのまま使うため、入力内容は保存されない（spec FR-020 / US3 シナリオ6）。

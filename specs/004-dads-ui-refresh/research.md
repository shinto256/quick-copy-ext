# Phase 0 リサーチ: DADS準拠UIデザイン刷新

**Feature**: 004-dads-ui-refresh | **Date**: 2026-09-02 | **Spec**: [spec.md](./spec.md)

## R1. DADSトークンの入手元

### Decision

デジタル庁公式リポジトリ `digital-go-jp/design-tokens` (v2.0.1, MIT) の `figma/tokens.json` を一次情報源とし、そこから必要な値をCSSカスタムプロパティとして `sidepanel.css` に転記する。npmパッケージ `@digital-go-jp/design-tokens` は導入しない。

### Rationale

- 公式ドキュメントサイト (design.digital.go.jp/dads/foundations/) はカラーとエレベーションの具体値を掲載しておらず、Figmaファイル参照となっている。実値はトークンリポジトリにのみ存在する。
- ライセンスはMITで、値の転記に制約はない。
- ノービルド方針のため、npmパッケージを依存に加えてもCSSへ反映する手段がない。値の転記が唯一の適合手段。

### Alternatives considered

- **npm `@digital-go-jp/design-tokens` を devDependency に追加**: ビルド工程なしではCSSに反映できず、package.jsonに使われない依存が増えるだけ。却下。
- **公式サイトの記述のみを根拠に近似色を自作**: 具体値が非掲載のため準拠を主張できない。却下。

### 参照

- https://github.com/digital-go-jp/design-tokens (`figma/tokens.json`, v2.0.1, MIT)
- https://github.com/digital-go-jp/design-system-example-components-html (`src/global.css`, `src/components/link/link.css`)
- https://design.digital.go.jp/dads/foundations/

## R2. ダークテーマの配色導出

### Decision

DADSのプリミティブカラースケール(各色相13段階)から、ダークテーマ用の値を選び直す。選定結果はコントラスト比の自動検査で検証し、基準を満たすことをもって「DADS準拠」とする。

### Rationale

- **DADSはダークテーマの配色を定義していない**。`tokens.json` にダーク用セットは存在せず、公式のexample componentsにも `prefers-color-scheme` の記述が一切ない。トークンは単一のライトテーマのみ。
- したがってダークテーマについてDADSが課す唯一の客観的基準はコントラスト比(テキスト4.5:1、非テキスト3:1)である。
- 既存機能([req-000006] テーマ手動切替)がダークテーマを提供済みで、これを廃止する選択肢はない。

### Alternatives considered

- **ダークテーマを廃止してライトのみにする**: 既存の承認済み機能を削ることになり、spec FR-021(既存機能の維持)に反する。却下。
- **ダークテーマはDADS対象外として現行の配色を維持**: SC-001が両テーマでのコントラスト比を要求しており、検証を免れない。却下。

- **両テーマで同一のセマンティックカラーを使う**: ダークでエラー色が基準割れするため不成立。却下。
- **ダークのカード面を SolidGray-800 にする**: 上記の通り4項目が基準割れ。却下。

## R4. 「隣接する面の色差」に3:1を求めるか

### Decision

タブ背景と地、カード面と地といった**面同士の色の差**には3:1を要求しない。選択状態の区別は文字色と文字の太さで担保する(spec FR-019)。境界線・アイコン・状態表示など、識別に必要な要素には3:1を要求する。

### Rationale

- WCAG 2.2 の達成基準1.4.11(非テキストのコントラスト)が求めるのは「UIコンポーネントの識別と状態の判別に必要な視覚情報」のコントラストであり、隣接する面の色の差そのものではない。
- 実際、DADS自身も選択タブの背景に Blue-50 (`#e8f1fe`、白地に対し1.14)を用いており、面の色差に3:1を課していない。
- 面の色差に3:1を課すと、ライトテーマで淡い選択背景が使えなくなり、DADSのパレット設計と矛盾する。

### 実装上の帰結

コントラスト比の自動検査のペア定義には、面同士の組み合わせを含めない。

## R5. フォーカスリング

### Decision

DADS指定の実装をそのまま採用し、テーマによる色の変更を行わない。

```css
:focus-visible {
  outline: 2px solid transparent;
  outline-offset: 2px;
  box-shadow:
    0 0 0 2px #ffd43d,   /* Yellow-300 */
    0 0 0 4px #000000;
}
```

DADSの実装例は `outline` と `border-radius` を用いるが、全要素へ一括適用すると各要素の角丸が上書きされて形が崩れる。二層を `box-shadow` で描くことで、要素自身の `border-radius` に追従させる(実機確認 2026-09-02 での修正)。

### Rationale

- 黒の外周とYellow-300の内側という二重構造で、背景色に依存せず視認できる設計になっている。
- ダークテーマ(地 `#1a1a1a`)では黒の外周が地に対し1.21となり単独では判別できないが、内側のYellow-300が地に対し12.21で視認を担保する。フォーカス表示全体としてWCAG 2.2の達成基準2.4.13(フォーカスの外観)を満たす。
- spec FR-017が「独自の色に置き換えてはならない」と規定しており、ダーク用に外周色を変更する選択肢は取れない。

### 実装上の帰結

コントラスト比の自動検査では、フォーカス表示について「二層のうち少なくとも一層が地に対し3:1以上」を判定条件とする。

## R6. タイポグラフィスケール

### Decision

DADSのテキストスタイルトークンから、狭幅UI向けに以下を採用する。

| 用途 | DADSトークン | font-size | font-weight | line-height |
|---|---|---|---|---|
| 項目名 | Dns-14B-130 | 14px | 700 | 1.3 |
| 項目の値・本文 | Std-14N-170 相当 | 14px | 400 | 1.7 |
| 補助テキスト・ラベル | Dns-14N-130 | 14px | 400 | 1.3 |
| ボタン・タブ | Oln-14N-100 / Oln-14B-100 | 14px | 400 / 700 | 1 |
| 入力欄 | Dns-14N-130 | 14px | 400 | 1.3 |

font-familyは `--font-family-sans: "Noto Sans JP", -apple-system, BlinkMacSystemFont, "Segoe UI", system-ui, sans-serif`。字間は全体に `0.02em`(DADS Std系の値)を適用する。

### Rationale

- DADSのテキストスタイルは Display / Standard(Std) / Dense(Dns) / Oneline(Oln) / Mono の5系統。狭幅UIには情報密度の高い Dns と、単一行UI要素向けの Oln が適合する。
- **文字サイズはDADS下限の14pxに統一する**。当初は本文16px / 補助14pxの2段階としたが、実機確認(2026-09-02)で文字を一段小さくする要望があり、FR-010の下限14pxまで下げた結果1段階になった。
- 本文と補助テキストが同サイズになるため、項目名と値の区別は**文字の太さ(700 / 400)と色(`--color-text` / `--color-text-muted`)**で行う。一覧の走査性はこの2軸で確保する。
- 行間は用途ごとに使い分ける。項目の値は `--line-height-body`(1.7)でFR-012の1.5倍以上を満たし、補助テキストは1.3、単一行のボタン・タブは1とする。
- モノスペース書体は同梱しない(R9参照)。現行UIにモノスペース表示の箇所が存在しないため。

### Alternatives considered

- **本文16px / 補助14pxの2段階を維持**: 当初案。実機確認で文字が大きすぎるとの判断により却下。
- **本文15px / 補助13px**: 要望に最も近いが、13pxがDADSの下限14pxを割り、FR-010・SC-002の変更とReqord要件の更新PRが必要になる。ユーザー判断により却下。
- **全テキストを Std-14N-170(行間1.7)で統一**: 行間が広くなりすぎ、狭幅パネルでの表示件数が過度に減る。用途別の行間使い分けを採用。

## R7. 余白・角丸・エレベーション

### Decision

**余白**: DADSのトークンリポジトリに spacing の定義は存在しない(未掲載)。公式ページが示す基準単位8pxに従い、以下のスケールを自前定義する。

```
--space-1: 4px   (最小: アイコンとラベルの間隔など)
--space-2: 8px   (基準)
--space-3: 12px
--space-4: 16px
--space-5: 24px  (中間)
```

**角丸**: DADS定義値 `4px / 6px / 8px / 12px / 16px / 24px / 32px / 9999px` から、コンポーネント種別ごとに割り当てる。

| コンポーネント | 値 |
|---|---|
| ボタン・入力欄・メニュー項目 | 8px |
| 項目カード・メニュー面・フォーム | 12px |
| タブ・ピル形状の要素 | 9999px (Full) |

**エレベーション**: DADS定義の8段階から3段階を使う。

| 用途 | トークン | 値 |
|---|---|---|
| 項目カード | (影なし) | 境界線で表現 |
| ポップアップメニュー | elevation-2 | `0 2px 12px 2px rgba(0,0,0,.1), 0 1px 6px 0 rgba(0,0,0,.3)` |
| 登録フォーム | elevation-6 | `0 10px 30px 6px rgba(0,0,0,.1), 0 3px 12px 0 rgba(0,0,0,.3)` |

### Rationale

- 余白はDADSがトークンとして公開していないため、公式ページの指針(基準8px、中間24px、大64px、「基準の倍率スケールから3〜5段階を定義」)に従って自前定義するのが唯一の準拠手段。64pxと32pxは狭幅パネルでは使い道がないため除外し、4px〜24pxの5段階とした。
- 角丸はDADS公式が「アスペクト比で見え方が変わるためコンポーネント毎に個別調整すべき」と明記しており、種別ごとの割り当てを行う。
- エレベーションは8段階すべてを使う必要がなく、本UIに存在する重なりは「ポップアップメニュー」「登録フォーム」の2種のみ。当初は「ドラッグ中の項目」にも影を用いる想定だったが、実機確認(2026-09-02)で並び替えをドラッグ&ドロップから▲▼ボタンに変更したため不要となった。

## R8. コントラスト比の自動検査の実装方式

### Decision

`sidepanel.css` を読み込んでカスタムプロパティの値を抽出し、テストコード側に持つ「実際に画面上で組み合わさる前景背景ペアの一覧」に対してコントラスト比を計算する vitest テストを追加する。

### Rationale

- **CSSを単一の情報源とする**。色値をJSモジュールに二重定義すると、CSSとJSが乖離したときにテストが実態を検証しなくなる。
- 既存テストは `src/` からimportして検証する形式(例: `tests/unit/maskDisplay.test.js`)。CSSを読む点は新しいが、`node:fs` で読んで正規表現で抽出するだけで、ビルド工程を必要としない。ノービルド方針と整合する。
- ブラウザでレンダリングして検査する方式(axe-core等)は、拡張のサイドパネルをヘッドレス環境で再現する仕組みが別途必要になり、ノービルド方針では重い。spec Assumptionsでも対象外と明記済み。

### 実装上の帰結

- 検査対象のペア一覧はテストコード内に定義する。CSSの実際の使用箇所との乖離は手動確認チェックリスト(FR-026)で補完する。
- ライト/ダーク両テーマのブロックをそれぞれ抽出して検証する。

### Alternatives considered

- **色値を `designTokens.js` に定義しCSSから参照**: CSSカスタムプロパティはJSから静的に生成できない(ノービルド)ため、二重管理になる。却下。
- **手動計測のみ**: 将来の配色変更で基準割れに気づけない。clarifyでユーザーが自動検査を選択済み。却下。

## R9. 書体の同梱

### Decision

**ウェイト軸を400〜700に限定した可変フォントのサブセット1ファイル(640KB)を同梱する。** `pyftsubset` で一度だけ生成してリポジトリにコミットし、以降の生成工程は持たない。**Noto Sans Mono は同梱しない。**

収録範囲: 常用漢字2136字 + ひらがな + カタカナ + 英数記号 + 全角記号 + 約物。

### 実測サイズ比較

| 方式 | ファイル数 | サイズ |
|---|---|---|
| Google Fonts css2 のチャンク(400のみ) | 124 | 2,727KB |
| 同上 ×2ウェイト | 248 | 約5.5MB |
| かな+英数のみ・可変 | 1 | 135KB |
| +常用漢字・静的400 + 静的700 | 2 | 724KB |
| +常用漢字・可変(軸フル) | 1 | 682KB |
| **+常用漢字・可変(軸400〜700)** | **1** | **640KB** |
| (参考) Noto Sans Mono 英数のみ・可変 | 1 | 18KB |

原本 `NotoSansJP[wght].ttf` は9.6MB。上表は実測値。

### Rationale

- **Google Fonts css2 経由は不成立**: ウェイトごとに124個の `unicode-range` 分割ファイルを返すため、2ウェイトで248ファイル・約5.5MBとなり、SC-007の1MB以内を大きく超える。手作業での管理も現実的でない。
- **可変フォントが静的2ファイルより有利**: 640KB対724KB、かつ1ファイルで済む。`font-weight: 400 700` の指定で両ウェイトを解決できる。
- **生成環境は追加不要**: Python 3.10 と Node 20 が既に環境にあり、使い捨ての仮想環境で一度生成してコミットすれば、プロジェクトに新たな依存もビルド工程も加わらない。ノービルド方針と整合する。

### 生成コマンド(再現用・一度きり)

```bash
python -m fontTools.varLib.instancer "NotoSansJP[wght].ttf" wght=400:700 -o var400_700.ttf
pyftsubset var400_700.ttf --output-file=NotoSansJP-subset.woff2 --flavor=woff2 \
  --unicodes="U+0020-007E,U+00A0-00FF,U+2000-206F,U+2190-2193,U+2212,U+25A0-25FF,U+2605-2606,U+3000-303F,U+3040-309F,U+30A0-30FF,U+FF01-FF60,U+FF61-FF9F,U+FFE0-FFE6" \
  --text-file=joyo_chars.txt --name-IDs="0,1,2,3,4,5,6,13,14"
```

生成物の検証結果: woff2形式、3128グリフ、2826 cmapエントリ、`wght` 軸400〜700。あ / ア / 亜 / 東京 / 住所 / 番地 / 漢字 / ABC / 123 / ・ / ー / 〒 / （） の収録を確認済み。

### Manifest V3 での配置

**manifest.json の変更は不要。**

- `web_accessible_resources` は不要。拡張のリソースには拡張自身のオリジンから読み込まれたページのみがアクセスでき、サイドパネルは拡張ページそのもの。この宣言は外部のWebページへ資産を公開する場合にのみ必要。
- `content_security_policy` の追加も不要。MV3の `extension_pages` 既定値は `script-src 'self' 'wasm-unsafe-eval'; object-src 'self';` であり、`font-src` を制約しない。

配置先は `src/sidepanel/fonts/`、CSSからは相対URLで参照する。

```css
@font-face {
  font-family: "Noto Sans JP";
  src: url("fonts/NotoSansJP-subset.woff2") format("woff2");
  font-weight: 400 700;
  font-display: swap;
}
```

`format("woff2")` と `font-weight` の範囲指定を用いる。`woff2-variations` は過渡期の記法で、Chrome/Edgeでは不要。

### font-display

`swap` を採用する。ローカルディスクからの読み込みでネットワークを介さないため、書体が適用されるまでの時間は640KBのbrotli展開分(初回数十ミリ秒)にとどまり、以降はデコード済みの書体がキャッシュされる。`swap` はテキストが不可視になる期間を作らない。

- `block` は最悪3秒の不可視期間を許容する代わりに再描画のちらつきを避ける選択肢だが、本件では不可視のリスクの方が問題。
- `optional` はブラウザが同梱書体の使用自体を省略することを許すため不適。

### Noto Sans Mono を同梱しない理由

`src/` 全体で `font-family` の宣言は `sidepanel.css:60` の1箇所のみで、モノスペースの使用箇所はゼロ。spec FR-008のモノスペース条項は「モノスペース表示が必要な箇所には」という条件付きであり、該当箇所が存在しない現状では充足済みとなる。将来、登録値の表示に必要となった場合は英数のみのサブセット18KBを追加すればよい。

### ライセンス(SIL OFL 1.1)

サブセット化は「Modified Version」の作成にあたるため、条項2により著作権表示とライセンス全文の同梱が必要。

- `src/sidepanel/fonts/OFL.txt` にライセンス全文を配置する。
- 生成時に name ID 0 / 13 / 14 を保持することで、著作権表示とライセンスURLが書体ファイル自体に埋め込まれる。保持による増加は1KB未満(640KB対641KB)で実質コストなし。
- Reserved Font Name は `Source`(Noto Sans JP は Source Han Sans の派生)であり "Noto" ではない。名称を "Noto Sans JP" のまま用いても RFN の抵触は生じない。

### 収録範囲の限界(planに引き継ぐ注意点)

UI自体の文言は固定でこちらが管理できるが、**項目名と値は利用者の入力**であり、常用漢字外の文字(人名用漢字、旧字体、絵文字)はシステム書体にフォールバックして異なる字面で表示される。これはspecのエッジケース「収録書体に含まれない文字…代替書体との混在で文字幅や高さが不揃いになってもレイアウトが崩れないか」に該当する。常用漢字は妥当な下限であって、全文字の保証ではない。

### Alternatives considered

- **Google Fonts の css2 API が返す分割済み woff2 を取得**: 248ファイル・5.5MBで SC-007 に反する。却下。
- **静的フォント2ファイル(400/700)**: 724KBで可変版より大きく、ファイル数も増える。却下。
- **同梱せず font-family の指定のみ**: 多くのWindows端末に Noto Sans JP が未インストールで、FR-008を実質満たせない。clarifyでユーザーがサブセット同梱を選択済み。却下。
